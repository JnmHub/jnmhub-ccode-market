## 物理断路器协议

### 闪退与静默失败

一旦目标程序发生静默闪退、无日志报错退出，或声称还原备份后依旧崩溃：

- 立即挂起一切对目标文件、补丁脚本、hook 脚本、JS/C#/二进制代码的修改动作。
- 将客观诊断写入 `artifacts/tasks/<task-id>/run/crash-diagnostics.md`，内容必须不少于 200 字符。
- 诊断必须包含硬件或系统级特征，例如 `EIP/RIP`、`ExceptionCode`、`0x...` 地址、WinDbg/x64dbg 输出、Event Viewer 记录、dump/stack 信息。

三步诊断顺序：

1. SHA256 核对当前受损文件与 `.clean.bak`，确认还原是否真实完成。
2. 抓取 Windows Application Error / Event Viewer 事件，提取异常码、崩溃模块和 fault offset。
3. 如工具可用，挂载 WinDbg/x64dbg/调试 MCP，捕获崩溃瞬间寄存器和调用栈。

未落盘这些证据前，不得提出“应该是某逻辑导致”的推理，不得继续 patch/hook。

### `.clean.bak` 哈希一致性

- 修改目标文件前，必须把干净备份写入 `run/<文件名>.clean.bak`，并在 `run/backup-manifest.md` 记录原始路径和 SHA256。
- `task-advance` 会扫描备份并核对原始文件哈希。
- 若哈希不一致且没有 `run/hash_mismatch_authorized.flag`，任务推进必须失败。
- 授权豁免只表示当前修改是受控修改，不表示验证完成。

## 什么不算证据

以下信号永远不构成完成或进展证据：

| 信号 | 为什么不算 |
|---|---|
| 脚本执行无报错 | 只说明代码没有抛异常，不代表目标行为达成 |
| Hook 已注入 | 代码存在不等于 hook 生效 |
| 文件已修改 | 写入内容不等于内容正确 |
| 进程已启动 | 启动不等于功能正常 |
| 代码逻辑上应该可以工作 | 推理不是验证 |
| ASAR 解包成功 | 解包不是业务逻辑还原 |
| Hook 代码已写入 | 注入、生效、产生预期效果是三件不同的事 |

唯一有效证据：

- 截图、命令输出、调试器输出、日志，其中能直接读出与 `completionCriteria` 匹配的内容。
- 用户明确确认成功。
- 反编译或调试结果中明确可见的逻辑路径，附函数地址、行号或调用栈锚点。

## Hook 不是调查手段

Hook、注入、拦截、patch 是实现手段，不是调查手段。

不构成调查的行为：

- 写 hook 来“看看会发生什么”。
- 注入代码来“尝试绕过”。
- 修改目标来“测试效果”。

调查阶段必须先用只读手段理解目标行为：反编译、调试器断点/单步、字符串搜索、xref、调用栈、内存/导入/资源观察。若无法说清“验证链是 A -> B -> C，我修改的是 C”，不得进入实现。

## 历史发现是假设

历史会话摘要、记忆、旧报告、WebSearch 结果只能作为假设，不能作为本轮的事实证据。只有本轮用工具重新验证后，结论才成立；验证过程与结论收口时写进 `report.md` 的「实现路径 / 坑点与经验」节（report-only 改造：原 `run/assumptions.md` 台账义务取消，载体改为收口报告）。

示例（正文声明即可）：

```text
假设: 上次会话称验证使用 crypto.publicDecrypt（依据: 历史会话摘要）
风险: 中 —— 如果错误，hook 点会偏离验证链
验证方式: 本轮用 inspector 或 trace 验证调用栈
```

## 进展声明格式

每次写入 `route-state.json` 的 `resultSummary`、推进 `execution.status`，或正文声称进展时，必须附带：

```text
进展: [一句话描述]
证据工具调用: [截图/测试/调试输出的 call_xxx ID，或 "用户确认: 原文引用"]
证据内容: [从工具输出中引用的具体文字]
```

没有证据工具调用 ID 或可读证据内容的进展声明，不得用于推进状态。

## 状态推进门控

`route-state.json` 的执行状态只能反映真实证据：

- `blocked`：等待用户或外部条件。
- `investigating`：分析阶段进行中。
- `implementing`：实现阶段进行中。
- `verified`：已有截图、测试、调试或用户确认能证明效果。

推进规则：

- `investigating -> implementing`：必须已经能书面说清完整验证链（入口→…→修改点的调用链锚点）；不要求任何过程文档存在。
- `implementing -> verified`：当前轮必须有验证类工具调用，且结果已读取分析。
- 任何状态 -> `verified`：必须有证据，不得凭“代码写完了”推进。

## 假设债务

任何“不确定”“应该是”“大概是”“根据记忆”“可能”的结论都是假设债务（report-only 改造：原 `run/assumptions.md` OPEN/VERIFIED/INVALIDATED 台账门禁取消；语义保留，载体改为收口 `report.md` 的「坑点与经验」节——记录假设内容、风险、影响与最终验证/排除结论）。

约束：

- 高风险假设禁止直接驱动实现，必须先验证。
- 中风险假设可以进入实现，但必须在验证环节闭合。
- 低风险假设可暂存，但收口前必须全部有结论（验证通过或排除），并在 report.md 留痕。

## 捷径暴露

调查/规划阶段跳过复杂分析步骤时，必须在正文显式声明：跳过了什么步骤、原因、可能的失败形态；收口时把该捷径及其后果写进 `report.md` 的「坑点与经验」节。声明捷径不是失败；不声明会让失败无法归因。

## 尝试计数语义

「同一方法连续 3 次失败」等止损规则只在统一的计数语义下才成立——本节定义适用于下文止损表格与硬止损的全部计数。三类动作区分如下（参数登记见 `docs/reference/acceptance-criteria.md` §13）：

| 类别 | 定义 | 计数与处置 |
|---|---|---|
| 同参重发 | 同方法、同参数、同目标原样重发 | 恒为 **0 次**（`references/fallbacks.md` 判级纪律，本表不放宽） |
| 变参重试 | 同方法、同目标、换参数/换输入 | 连续 3 次无果 → 该**探针**标记 PARKED（轻转向）；不等于方法族耗尽 |
| 路线内迭代步 | 长视距路线内推进一个结构单元（一个 handler、一段 trace、一条指针链、一层协议） | 只有**零信息步**计入失败计数 |

- **失败的定义**：一个动作结束后，假设空间未缩小、目标数据未取得、且未产出可登记的 clue/证据，计为一次失败。
- **负知识步不是失败**：排除一个假设 = 缩小假设空间 = 进展。排除类动作在正文登记（或追加进可选的 `state/clues.md` 账本）后，连续失败计数清零。
- **预算重置条件（与通道层预算律同构）**：取得目标数据、排除假设、缩小假设空间三者任一发生，连续失败计数清零。
- 通道层预算律（K=12）约束的是**工具通道**的调用预算；本节约束的是**方法/路线**的止损计数。两者独立计数、互不替代。

## 路线预算分级

止损阈值不是全局常数，按 `task.json.protectionTier` 与路线类别分级（参数登记见 `docs/reference/acceptance-criteria.md` §13；任何调整须附实证，禁止无锚点调参）：

- **L1 基线**（T0–T2 / 普通探针）：同一方法连续 3 次失败 → 转向。现行规则不变。
- **L2 结构化防护**（T3–T4：壳、反调试、加壳 .NET、多层校验、SSL Pinning）：探针预算对齐通道层 K=12（复用 `references/fallbacks.md` 预算律双锚点，不设新常数）。
- **L3 深水路线**（T5–T6，或任一 tier 命中：虚拟化/去虚拟化、反作弊内核对抗、rootkit、VM bytecode、强混淆多层）：不按失败次数止损，按**工作量单元检查点**推进——每完成 N 个结构单元做一次检查点，判据 = 自上一检查点以来新增 clues/evidence 数；**检查点零新增**才允许按「转向动作四级阶梯」升级。各专题单元定义：VMP 见 `references/vmp-unpack-playbook.md`；游戏逆向、恶意软件、.NET、协议专题见各 reference「止损衔接」节。

## 止损与反思

触发任一条件时进入 retrospective：

| 条件 | 信号类型 |
|---|---|
| 同一文件被修改超过 3 次，或补丁版本超过 3 个 | 版本膨胀 |
| 同一类操作循环 2 次 | 循环试错 |
| 同一方法连续 2 次失败 | 方向错误 |
| 同一方法族累计 3 次失败 | 方法族耗尽 |
| 绕过手段产生副作用但未解决核心问题 | 表面绕过 |
| 无法说清目标验证链与修改点关系 | 根源不明 |
| 用户明确指出方向不对 | 外部否定 |

本表触发的是**复盘**，不是路线判死：进入 retrospective 不等于方法族耗尽。L2/L3 路线的路线判死只由上文分级预算（K=12 / 检查点零新增）决定；预算未耗尽时，复盘产出的是缩范围/换通道后的同路线新探针，而非弃线。

反思序列：

1. 输出根因分析（retrospective 语义由 closeout 的 partial / infeasible 门禁承接——收口时写 `report.md` 的「未竟事项」节）。
2. 回答“我跳过了什么复杂步骤导致循环/失败？”
3. 把方法、结果、证据、跳过步骤在正文写清；需要断电续跑时可追加进 `state/clues.md` / `state/route-plan.md`（可选骨架，非义务）；收口时汇入 `report.md` 的「坑点与经验 / 实现路径」节。
4. 选择完全不同的方法，或向用户请求方向。

硬止损：

- 同一方法连续 3 次失败：标记 `EXHAUSTED`，按「转向动作四级阶梯」升级——L2/L3 路线按上文分级预算执行，探针预算未耗尽时不得判死整条路线。
- 累计 2 次 retrospective 无进展：不得开放式求助。请求方向时必须附「已排除路线矩阵 + 剩余未评估路线 + 每条剩余路线的首个最小 probe」，把停摆转化为可决策清单。
- retrospective 生成新切入点时，禁止生成与已 EXHAUSTED 方法族或 `task.json.userRejectedApproaches` 同族换皮的切入点；新切入点必须引用上一轮失败证据中的新事实。
- 验证失败且存在未验证高风险假设：回到调查环节补齐验证链。
- 根源不明时禁止写绕过代码：回到调查环节追完整验证链。

## 转向动作四级阶梯

「必须转向」不是单一动作。按序升级，只有第 3/4 级才是真正的「切换线路」；跳级换路线等于用更贵的动作处理本可便宜解决的问题：

1. **缩范围**：把当前方法的对象缩小一级（整函数 → 分支簇 → 单 handler → 单指令语义 / 单层协议 / 单条指针链）。先例：工具降级阶梯的「缩范围探活」。
2. **换工具/通道**：按 `references/fallbacks.md` 降级阶梯换接口家族或通道。
3. **换路线**：在专题路线矩阵（如 VMP `toolRoutes`）内换 route；原路线置 `failed` 并写明放弃证据，不得静默丢弃。
4. **升级协作**：multi-agent 派工（显式 opt-in）或向用户请求方向（按硬止损格式附「已排除路线矩阵 + 剩余路线 + 首个最小 probe」决策清单）。

## 搜索门禁

以下信号要求暂停当前路径执行 WebSearch：

- 发现新保护特征但未搜索过该类型。
- `protectionTier >= T3` 且未搜索过。
- 连续 2 轮工具调用无进展。

WebSearch 后的动作（report-only 改造：原 `state/external-research.md` 建档门禁与 T3+ 物理阻断已退役，调研结论的载体改为收口报告）：

1. 调用搜索。
2. 正文说明检索结论（query、结果数、关键发现）。
3. 高价值线索可追加进 `state/clues.md`（append-only 账本，可选）；调研结论收口时写进 `report.md` 的「坑点与经验 / 专题发现」节。

## 目标理解锚定

以下任一条件触发时，读取 `task.json.objective`，用一句话回答：“当前操作是否直接服务于 objective 中的核心动词？”

- 创建新 patch 版本。
- 累计约 20 次工具调用。
- 用户表达不满或质疑。

若答案是否，立即停下并重新评估方向。

## 历史失败案例：Typora 激活

失败模式：AI 写了 patcher 脚本，脚本跑完无报错，未截图验证就将状态推进为“等待用户验证”。用户要求截图后，截图显示激活对话框仍弹出。

跳过步骤：

- JSC 字节码分析。
- ASAR 闪退根因。
- 指纹差异调查。
- deviceId 来源验证。

教训：

- “脚本无报错”不等于任务完成。
- 每个跳过的复杂步骤都是潜在失败原因。
- 规则写清楚不等于会被执行，必须变成任务产物和工具门禁。
